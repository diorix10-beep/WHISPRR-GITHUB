# WHISPRR local Supabase development

This checkout has an isolated local Supabase stack for offline WHISPRR and CHIMERA development. The two frontends remain separate applications while using the restored local ecosystem backend. The normal local workflow never links to or writes to the hosted project.

## Daily start and stop

From the repository root:

```bash
npm run supabase:local:start
npm run dev:whisprr:local
```

Open WHISPRR at `http://127.0.0.1:5173`, Supabase Studio at `http://127.0.0.1:54323`, and local test emails at `http://127.0.0.1:54324`.

Stop the backend with:

```bash
npm run supabase:local:stop
```

To run CHIMERA instead (or in a second Terminal while WHISPRR is running):

```bash
npm run dev:chimera:local
```

Open CHIMERA at `http://127.0.0.1:5174`. The start command generates ignored `.env.local` files for both frontends with only the local API URL and local public anon key. Vite automatically prefers these files during local development. Existing production environment files and Vercel configuration are not changed.

## Restore the verified offline snapshot

The local restore uses the verified backup at `~/Documents/WHISPRR-BACKUP/2026-08-21-gcknzlnumcryvqjvjnyg` by default:

```bash
./scripts/supabase-local.sh restore-backup
```

This resets only the local database, applies every migration, imports the compatible Database/Auth/Storage metadata snapshot, and uploads the 18 Storage files. To use another backup, pass its directory as the second argument.

## Database migrations

Create every migration through the CLI:

```bash
supabase migration new descriptive_change_name
```

Edit only the generated SQL file, then apply pending changes locally:

```bash
supabase migration up --local
supabase migration list --local
```

To prove the complete history can rebuild from nothing:

```bash
npm run supabase:local:reset
npm run supabase:local:test
```

`reset` is destructive only to the disposable local database. Restore the backup snapshot afterward if production-like local data is needed again.

## Edge Functions

The backed-up `summarize-thread` function is in `supabase/functions/summarize-thread`. Copy `supabase/.env.example` to the ignored `supabase/.env.local` and add a development-only `OPENAI_API_KEY` to exercise its external OpenAI request. Then run:

```bash
npm run supabase:local:functions
```

Never commit `supabase/.env.local` or place a service-role/secret key in a `VITE_` variable.

## Local versus production environment values

Local frontend values live only in ignored `apps/whisprr/.env.local` and `apps/chimera/.env.local`:

- `VITE_SUPABASE_URL=http://127.0.0.1:54321`
- `VITE_SUPABASE_ANON_KEY=<local anon key generated by the CLI>`

Production values remain in the deployment provider and existing production environment configuration:

- `VITE_SUPABASE_URL=<hosted WHISPRR URL>`
- `VITE_SUPABASE_ANON_KEY=<hosted WHISPRR public key>`
- backend-only service/secret keys must remain server-side and must never use the `VITE_` prefix.

## Applying an approved migration to production later

Do not use these steps until the hosted project is available and the migration has been reviewed and backed up again.

1. Rebuild and test locally with `npm run supabase:local:reset` and `npm run supabase:local:test`.
2. Review the migration SQL, RLS ownership predicates, `USING` and `WITH CHECK`, function privileges, Storage policies, and `git diff`.
3. Create a fresh production backup.
4. Explicitly link the CLI to the WHISPRR project only for the controlled release window.
5. Run `supabase db push --dry-run` and inspect the exact pending migration list.
6. After explicit approval, run `supabase db push` once, verify production, and immediately run `supabase unlink` to return this checkout to local-only mode.

No link, push, migration, reset, restore, pause, delete, or write was performed against production during this setup.

## Local limitations

- Google/Apple OAuth requires separate provider credentials and localhost callback configuration; email/password Auth works locally now.
- Auth emails are captured by Mailpit and are not delivered to real inboxes.
- `OPENAI_API_KEY` is intentionally absent, so `summarize-thread` proves its local route but returns a clear missing-secret response until a development key is supplied.
- Hosted billing, custom domains, production SMTP, platform logs/analytics, backups, and dashboard-only settings are not reproduced by the local stack.
- Storage image transformations and other hosted-plan features may differ locally.
- The backup is a point-in-time snapshot. New hosted changes made after 2026-08-21 are not present locally.
- Existing wallet/ledger foreign-key ordering currently makes the Auth admin user-deletion endpoint fail until that user's local SHARDS/VELLUM ledger rows are removed. The smoke test handles only its disposable local test account; production was not changed.
- CHIMERA's browser-only Vite server does not execute the Vercel routes under `apps/chimera/api`. AI chat, scene illustration, guided turning points, Stripe checkout, and Stripe webhooks therefore need a separate local Vercel-functions setup plus development-only provider secrets. Core Auth, Database, Realtime, and Storage development do not depend on those routes.
- External AI translation and voice features still require their respective development API keys and internet access.

## Verify CHIMERA locally

With Docker and the local stack running:

```bash
npm run supabase:local:test:chimera
npm run build --workspace=chimera
```

The smoke test creates and removes only a disposable local Auth user. It verifies the tables used during CHIMERA startup, character/story/world/persona/lorebook reads, wallet RPCs, and restored Storage buckets. It refuses to run if the API URL is not the fixed localhost address.
